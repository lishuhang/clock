## 用户偏好与工作边界

用户要求先根据真实日志、生产文件和远程仓库状态判断原因，再决定是否修改。生产环境不得直接试验；应在隔离副本测试、以白名单打包、校验候选后再部署。用户明确要求避免无效提交；对远程已存在的内容，后台任务应安全跳过而非覆盖、等待输入或通过重试形成重复网络操作。需要完整 v1.20 发行包、README 和增量交接记录。

## 根因结论

日志显示的不是新的 daily 内容被无限抓取，而是 **daily 子脚本在后台自动模式中遇到远程已存在的图片后，输出了覆盖确认提示并等待标准输入**。主调度器等待 1,800 秒后将其当作超时，按既有策略重试三次。每次重试都会重新枚举同一篇 2026-08-18 早报、重新下载图片和本地写入 Markdown，随后再次停在同一个覆盖提示。因此用户观察到重复爬取；如果不修复，表现会持续到三次重试耗尽，而不是无限的独立新文章处理。

远程核对表明当天 daily 仓库只有一条早报发布提交，图片仓库只有一次封面上传和一次自动压缩提交。主博客仓库未接收当天 daily 文件；photos 仓库当日也没有更新。因此此次问题没有造成多次 daily GitHub 提交，主要风险是后台阻塞、重复抓取、无效下载和延迟后的重试。

## 踩坑与后续注意事项

1. 不要把“脚本正在重试同一阻塞子进程”误判为“远程仓库发生了无限提交”。应同时核对日志中的提示语和远程提交历史。
2. 对自动任务，覆盖确认属于错误的交互方式；必须有明确的非交互模式。手动命令仍可保留覆盖确认，但自动路径不得调用它。
3. daily 的“远程最新日期”不足以防止同日重复处理，因为专辑查询的时间边界包含该日期。必须用远程完整日期集合过滤候选。
4. `run_script` 全局关闭空标准输入是兜底，不替代子脚本自己的 `--non-interactive` 语义。新加入的自动子脚本仍应显式实现安全的无交互行为。
5. 主博客现有自动范围抓取机制仍会获取指定日期后的候选文章，但 v1.20 在远程文章已存在时安全跳过，避免阻塞或覆盖。若未来需要彻底减少 blog 的抓取网络量，应另行设计基于远程文章 URL/日期的差集，不要在本轮顺带改动。
