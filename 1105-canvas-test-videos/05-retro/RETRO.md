# 复盘记录：为什么烧了大量 token，改了五轮，还是会出低级错误

> 2026-11-06 · v6 复盘轮
> 输入：老板 17:56-17:58 审片反馈（①竖版字幕和音频不对位 ②横版也不对位 ③横版里贴的视频被拉伸、比例尺不对）+ 仓库全量工作记录复原
> 结论先行：**三处问题全部是"已修复问题的回归"，没有一处是新问题。回归的共性根因是：修复成果存在于"会话记忆和沙盒文件"里，而不存在于"仓库和机器门禁"里。**

---

## 一、三处问题的证据链与根因

### 问题1：字幕与音频不对位（竖版+横版，最严重）

**表象**：v5 成片字幕与配音错位，观众几分钟内即可感知。

**证据链（本轮实测复原）**：

| 版本 | 组装脚本烧录的字幕源 | 时间轴性质 | 结果 |
|---|---|---|---|
| v3（修复轮） | `ep1_subtitles_real.json`（沙盒） | whisper 词级实测，365 卡 | ✅ 音画同步，老板验收通过 |
| v4 | `ep1_subtitles_v4.json`（沙盒） | 同上派生，365 卡 | ✅ 同步保持 |
| **v5** | **`04-ep1-production/ep1_subtitles.json`（仓库）** | **v2 时代旧对齐，385 卡** | ❌ **同步复发** |

本轮用字符流对齐法实测两个文件的时间轴偏差（同一句话的开声时刻差）：

```
旧 JSON vs whisper 实测（21 个采样点）：
  1:03 处 -6.9s → 1:44 处 -12.9s → 2:17 处 -17.7s → 3:54 处 -23.6s
  （漂移谷值）→ 7:54 处 +27.8s（漂移峰值）→ 片尾回归 0
  86% 采样点偏差 >0.5s；最大偏差 27.8 秒
```

这不是"轻微不准"，是**字幕比配音早/晚了小半分钟**——正是铁律 13 里白纸黑字记载过的"字数权重估算全片可漂移 ±27s"。同一个坑，原样踩回去。

**根因链（五步连环，缺一不可）**：

1. **修复成果未入库**：v3 真正使用的 whisper 字幕卡 JSON（`ep1_subtitles_real.json`/`ep1_subtitles_v4.json`）只存在于沙盒工作目录，从未 commit。项目章程明明写着"每完成一个可交付小步立即 commit+push 防沙盒回收"，但"交付物"被狭义理解为成片/srt/skill，**对齐中间件这个"防复发疫苗"本身没有备份**。
2. **沙盒回收后错误文件顶上**：v5 会话在新沙盒重建时，仓库里只有一个名字很合理的 `ep1_subtitles.json`——它是 v2 时代的旧产物，但**没有任何元数据说明它是过期的**。智能体拿到它，当成了权威源。
3. **没有对账步骤**：仓库里明明躺着权威真值 `output/字幕v3.srt`（365 卡、老板验收过的那一版）。v5 若在烧录前拿 JSON 与它对一次账（卡数、首卡时间、任意抽样 diff），30 秒就能发现不一致。但流程里没有这一步。
4. **QC 门禁全是"技术健康度"**：G1-G7 查坏帧/帧数/时长/分辨率/响度/黑屏/元数据——**没有任何一条检查字幕是否对得上配音**。字幕烧错时间轴，七道门禁全部绿灯放行。
5. **长上下文的注意力稀释**：到 v5 会话，上下文里堆着五轮修复的全部细节。铁律 13 的字还在，但"当前要用的这个文件是不是铁律 13 说的那个文件"——这一步关联推理，在超长上下文里失效了。RESUME.md 还写着"不要重新调研"，进一步抑制了复核动机。

### 问题2：横版里贴的视频被拉伸、比例尺不对

**表象**：横屏版里《牌子》《丧尸清道夫》、实测片段、抽卡录屏全部比例失调。

**证据链**：

v4/v5 的 bg 视频处理链（`assemble_v4.py`/`assemble_v5.py` 的 `cmd_bg`）：

```python
"scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920"
```

`increase` + crop = **放大铺满** 9:16 竖屏。对真实影片素材意味着：

| 素材 | 源分辨率 | 源宽高比 | 放大倍数 | 横向可见比例 |
|---|---|---|---|---|
| 《牌子》 | 1280×720 | 16:9 | 2.67× | 31.7% |
| 《丧尸清道夫》 | 1280×548 | 2.34:1 | 3.50× | 24.1% |
| 抽卡延时录屏 | 2880×1800 | 16:10 | （v4 已知妥协）"只保留水平中部 35%" | 35% |

横屏版再从 1080×1920 裁出 Y555~1365，最终观众看到的是**源画面被放大 3~6 倍后挖出来的一小块**——不是拉伸变形，而是比拉伸更糟的"暴力裁切放大"。老板说"比例尺不对"，完全属实。

**根因链**：

1. **规格层的错误被忠实执行**：canvas 母版规范层白纸黑字写着"背景层（图/视频/渐变）按需**拉伸铺满** 9:16，不加遮罩、不留黑边"（`#bg-layer > video { object-fit: cover }`）。这条规则为**抽象底图/氛围图**设计，v3 引入 B站真实原片做叠底，v4 又把"原片前景展示"升级成独立镜头（S02a/S03a 纯净前景），**视频的角色从"氛围底"变成了"展示主体"，但缩放规则没有跟着改**。代码无罪，规格有过。
2. **"已知妥协"没有触发设计复审**：v4 生产记录里明明白白写着"亮色屏幕录像切 9:16 只保留水平中部 35%"——被记进"已知妥协"栏后就没有人再看一眼。**一个需要老板看画面才能发现的问题，被降级成了文档里的一行小字。**
3. **QC 不测素材几何**：没有任何门禁检查"嵌入视频的显示比例 == 源比例"。

### 问题3（本轮顺带发现）：进度条在 372s 切点重置、永远只走到 54%

**表象**：老板没提（前两轮也没提），但这是 v4 引入、v5 未察觉的真实回归，横竖屏都中招。

**证据链**：v3 的 `ffmpeg_master_v2_seg.py` 有段偏移逻辑：

```python
def gen_seg_cmds(total, t0, t1, path):
    """sendcmd 偏移版：段内时间 = 全局 - t0，首条命令设在 0.0。"""
```

v4 重写 final 段时换成了 `gen_progress_cmds(TOTAL, cmds_file)`——**从 0 生成到 740s，段 B 的 368 秒里只执行到前一半的指令**。结果：进度条 0→54%，中点跳回 0，再 0→54%。

本轮 v6 实测（vfinal 抽帧量顶部 8 行橙色像素宽）：

```
v5 逻辑推演: 切点前 539px → 切点后 ~9px（重置）→ 片尾 ~542px（永远不满格）
v6 实测:     切点前 539px → 切点后 544px → 片尾 1078px（期望 1080）✓
```

**根因**：重写管线代码时，**没有对照旧实现逐条核对"已验证行为"**。旧代码里那行 `t - t0` 是 v2 时代踩坑换来的，重写者不知道它为什么存在，它就消失了。这是软件工程里最经典的回归类型：**修复知识只活在代码里，没有活在断言里**。

### 附：老板提到但属于行为模式的问题——"找B站素材没按文档写法，先探索了一轮才回去翻文档"

worklog 证据：1020 轮"B站API直连412（数据中心IP风控），snapany首次解析后登录墙"——先撞了 API 直连和第三方解析站，才回到文档记载的 `playurl html5 游客通路`。而这条通路在 `video-downloader-skill.md` 的平台路由表里是**第一行第一列**。

**根因**：
1. **探索是默认动作，查表不是**。智能体接到"下载B站视频"这个子任务时，上下文里路由表的位置已经被几万 token 的其他内容推远，"记得大概有个方法"的幻觉自信压过了"先精确查表"的纪律。
2. **文档没有被设计成"强制路由"**。SKILL.md 的素材来源决策是一句话带过，没有"任何外部平台操作前必须先 grep 路由表并在 worklog 引用所循文档行"的硬约束。

## 二、深层问题：为什么五轮修复、大量 token 烧进去，还是拦不住低级错误

### 2.1 token 花在了"生产"上，没有花在"防回归"上

回看 v3→v5 三轮修复的 token 去向：whisper 对齐管线、帧数精确架构、黑底换肤、B站素材通路、43→46 镜重排、间隔号清零、logo 补齐、4:3 安全框整改、推箱子/盖章/阶梯动画化……**全部是"往前加新能力"**。而"防回归"的投入是零：没有一条为已修复 bug 建立的自动断言，没有产物血缘清单，没有重写对账制度。

> **低级错误反复出现的本质：每个修复都解决了"这一次的错"，但没有人把"这一类的错"变成机器拦得住的东西。**

于是修复成果的存续完全取决于"智能体在下一次会话里还记得多少"——这是最不可靠的存储介质。

### 2.2 长上下文是负资产：记忆越满，遵循越差

五轮会话的教训、铁律、踩坑记录全部堆在 SKILL.md（31 条铁律 + 5 个 reference 文件）和超长对话里。但**规则的数量和遵循率不成正比**：

- 铁律 13 写着"禁字数权重直接投产"——v5 烧字幕时没有任何机制强制核对当前文件是不是字数权重产物。**散文规则对人有效，对概率性的模型输出只能靠断言兜底。**
- RESUME.md 的"不要重新调研"是为省 token 设计的，但它同时压制了"对既定假设做廉价复核"的动作。省 token 的初衷，反而造成了烧掉整轮重制的浪费。
- 上下文越长，早期内容的有效权重越低。v3 的教训在 v5 会话里已经"考古层化"了。

**正确姿势不是"更长的记忆"，而是"更小的信任面"：把必须成立的不变量写进 setup 断言和 QC 门禁，让每一轮会话开局就被机器校验一遍。**

### 2.3 备份纪律执行了一半：备了"作品"，没备"事实"

章程的入库规则防住了 canvas 页、脚本、成片（所以本轮能完整重建），但漏掉了**决定正确性的中间产物**：

- whisper 字幕卡 JSON（问题1 的直接死因）
- `para_dl.py`（323MB 并行下载器，v5 用完即丢，本轮重写）
- `ep1_shots_v4.json`（46 镜权威分镜——幸运的是它被顺手存进了 skill 的 examples/，但存的位置连 v5 的脚本都没认出来，`SHOTS` 还是指向沙盒路径）

而且**没有任何文件标注自己的血统**（谁生成、依据什么、被谁验收过）。仓库里 `ep1_subtitles.json` 和（假想中的）`ep1_subtitles_real.json` 名字同样体面，新旧无从分辨。

### 2.4 QC 测的是"技术健康"，不是"用户感知"

七道门禁（坏帧/帧数/时长/分辨率/响度/黑屏/元数据）回答的都是"这个文件是不是一个合格的视频文件"，没有一道回答"**这个视频是不是老板眼睛看到会点头的东西**"。老板的三个感知维度——字幕跟不跟得上嘴、画面比例正不正常、进度条像不像话——恰好全部在门禁之外。VLM 抽帧目检做了，但抽的是"画面有没有乱码/溢出"，没有按感知维度设计检查项。

### 2.5 一个反直觉的发现：目检本身也会说谎

本轮验证时，VLM 把源片《牌子》36.0s 处的**贴地特写镜头**（狗被拖行、只有脚和地面——影片自身的构图）误判为"画面被裁切拉伸"。后经像素级 diff（bg 产物 vs 手工同链缩放的参考帧，窗口区平均差 5.1，编码噪声量级）证明几何完全正确。

教训：**感知级检查（VLM/人眼）会产生误报和漏报，必须与几何/数学断言互为犄角**。门禁设计要分层：能用像素断言的绝不靠目检，必须目检的（内容正确性）要用锚点对照而不是自由描述。

## 三、修复架构：把"记得"换成"拦得住"

v6 落地的不是三个补丁，而是一套防回归机制（三项修复只是它的第一次运行）：

### 3.1 单一事实源 + 血缘标注（治：问题1）

- 新建 `ep1_subtitles_whisper.json`：从仓库中幸存的权威交付物 `字幕v3.srt` 反向重建，文件头带 `_provenance` 字段（对齐方法、来源、版本史、校验说明）。
- **从此字幕只允许这一个事实源**。旧的 `ep1_subtitles.json` 在版本史里标注"作废，仅存档"。

### 3.2 setup 段血缘对账断言（治：问题1 的"缺对账"环节）

`assemble_v6.py setup` 段在跑任何生产步骤之前，先逐卡对账：canonical JSON ↔ `字幕v3.srt`，365 卡、文本全等、时间差 ≤10ms，任何一项不符直接拒绝开工：

```
[setup] G8 前置对账 PASS：365 卡与 字幕v3.srt 逐卡一致（±10ms）
```

### 3.3 bg 双模式 + G9 几何断言（治：问题2）

- `fit` 模式（影片作主体）：原生比例嵌入 4:3 舞台（16:9→1080×608、2.34:1→1080×462、16:10→1080×675），pad 色与全片底色一致。
- `cover` 模式（影片作氛围底，仅限竖版源）：铺满 4:3 舞台再裁，全宽可见无拉伸。
- G9 门禁：每个 bg 镜抽帧实测视频窗口矩形，与 ffprobe 源分辨率推算的期望矩形比对（±6px）。v6 实测 6/6 通过，最大偏差 3px。

### 3.4 段偏移恢复 + G10 进度条断言（治：问题3）

- `gen_seg_cmds(total, t0, t1)` 恢复 v2_seg 的段内偏移语义，并写明"丢失即回归"的注释。
- G10 门禁：切点前后 ±2s 与片尾三处抽帧，量顶部橙色像素宽度，断言单调连续 + 终值 ≈1080。v6 实测 539→544→1078。

### 3.5 锚点式目检（补：VLM 目检的正确用法）

不再"自由描述画面"，改为**先算出期望、再对照实读**：26.71s 处字幕必须是"这些案例很容易给人一种错觉："（v3 修复验证点）、314.27s 处必须是"最低需要充值多少钱？"……四个锚点横竖屏八帧全部命中。几何争议一律回到像素 diff 裁决。

### 3.6 产物入库清单（治：2.3 的备份半吊子）

本轮起，**决定正确性的中间产物与作品同级入库**：`ep1_subtitles_whisper.json`（权威字幕）、`assemble_v6.py`、`make_canonical_subs.py`、`para_dl.py`（重建版）、`ep1_shots_v4.json`（从 skill examples 正名回工作目录）。

## 四、遗留风险与已知妥协（不藏）

1. **v6 未改 canvas 页面**：46 镜帧由仓库当前 canvas 页（v5 整改版）重渲，画面与 v5 一致——本轮只修错误，不动已验收的设计。
2. **S02b/S03b 证据卡入场时刻仍是字符占比估算**（v4 已知妥协，误差 ≤1s，本轮未处理——不在本次反馈范围）。
3. **1.1x 提速重采样帧数漂移**：竖屏 20205 帧 vs 理论 20192（+13 帧，0.43s），G2 容差 ±15 内；这是 setpts/fps 重采样的固有行为，若要绝对精确需改"先提速后烧字幕"架构（改动大，未做）。
4. **VLM 对贴地特写等特殊构图仍可能误报"变形"**——已用像素断言兜底，但人工审片时若再遇类似争议，先跑几何对账再下结论。
5. **三篇连载的 skill 通用性**：本次 skill v2.0 规整（见 `03-skill/`）剥离了项目专属参数，但"第二/三篇投产"是对新 skill 的第一次真实检验，建议照 v6 模式小步跑。

## 五、给流程的三句话（写给下一个智能体，也写给老板）

1. **凡是老板验收过的东西，它的"再生产依据"（数据+脚本+断言）必须同刻入库，并在文件头写清血统**——作品入库不算备份，事实入库才算。
2. **修复一个 bug 的完成标志不是"这次对了"，而是"下次想错都错不了"**——没有断言的修复等于没修。
3. **长会话不可信，开局先对账**——任何一轮新会话，先跑 setup 断言把旧世界的账全部对平，再动第一根手指。
