## 根因与证据

最新两篇同步文章为：

| 日期 | 文章 | 已发布 Markdown 引用 | 图床仓库实际文件 | 结论 |
|---|---|---|---|---|
| 2026-08-12 | 《我们就是会不由自主地宽容豆包》 | 多个 `01.png`、`04.png`、`12.png`、`13.png` 路径 | 对应文件已转换为 `01.jpg`、`04.jpg`、`12.jpg`、`13.jpg`，少数原 PNG 保留 | 多处扩展名错配。 |
| 2026-07-25 | 《请 Gemini，给数学不及格的文科生讲解王虹的菲尔兹奖》 | `01.png`、`02.png`、`04.png`、`05.jpg` | 图床仅有 `01.jpg`、`02.jpg`、`03.gif`、`04.jpg`、`05.jpg` | 三个 PNG 引用不存在。 |

第一篇公开页面的浏览器检查显示，存在的 `02.png`、`03.png` 可成功加载，而引用不存在文件的题图加载尺寸为 0。因此图床路由与站点 Liquid 机制正常，不是 weserv、Pages 或图床仓库整体不可用。

根因在 `04_convert-blog.py`：脚本先生成正文 `content` 和题图 `cover_github_url`，再下载并调用 `compress_and_convert_image()`。后者会把不透明 PNG 等转换为 JPG 并正确上传新文件，但旧实现仅更新内存 `image_mapping`，没有回写已生成正文和 front matter，导致 Markdown 留下旧扩展名路径。

## v1.22 实现

1. 新增 `rewrite_converted_image_urls(content, cover_github_url, replacements)`，将转换前/后 URL 映射同步回写至全部正文图片链接与题图字段。
2. 图片下载循环维护 `converted_url_replacements`；每个格式转换完成后记录旧公开 URL 到新公开 URL 的替换。
3. 所有图片下载完成、写 Markdown 前执行回写；透明 PNG 与没有格式转换的文件不修改。
4. `keepitrun.py` 更新为 `VERSION = "1.22"`、日期 `2026-08-21`，并在 `VERSION_TASK_CHANGES` 仅标记 `blog`。因此升级不会触发 RSS、daily 或 Photos 重跑。
5. README 更新为 v1.22，写明修复语义、版本感知范围和发布记录。
