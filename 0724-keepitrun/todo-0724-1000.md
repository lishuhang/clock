### 工作 B: 修复 lishuhang.me 图片显示问题（皮肤级，无插件）

**用户报告**: 所有文章图片 URL 缺少 `/img/` 段，`_config.yml` 的 `image_prefixes` 配置正确但皮肤未遵守。示例：

#### image_prefix 修复历程（6 次失败的插件迭代）

| 迭代 | 策略 | 问题 |
|------|------|------|
| 1 | Generator, priority :high | 修改 `post.content` 但 Jekyll 渲染器重新读取内容，rewrite 丢失 |
| 2 | `:post_render` hook | hook 触发了 1454 次但 regex 未匹配（日志无 Rewrote 行） |

| 5 | 扩展 regex 处理绝对 URL | 封面图仍未修复；用了 `next` in gsub block 导致全部失效 |
| 6 | 移除 `next`，用 negative lookahead | 内容图+封面图修复，但**用户 rerun job 后又失效** |

**核心问题**: Jekyll 4 的 `:post_render` hook 修改 `post.output` 在某些构建环境下不可靠（可能是 Jekyll 版本差异、CDN 缓存、或构建器内部行为）。

#### 最终方案：皮肤级 Liquid 修复（commit `2583bf2`）

**删除** `_plugins/image_prefix.rb`。

**修改 4 个皮肤文件**，直接用 Liquid 引用 `site.image_prefixes`：

##### 1. `_layouts/post.html` — 文章页
```liquid
{%- assign img_prefix = site.image_prefixes.first.prefix -%}

<!-- 题图 -->
{% if page.image and page.image != '/' %}
{%- assign img_path = page.image | remove_first: '/' -%}
{%- assign cover_url = img_prefix | append: img_path -%}
<img src="https://images.weserv.nl/?url={{ cover_url | url_encode }}&output=jpg&q=80"
     data-original="{{ cover_url }}">
{% endif %}

<!-- 正文：用 replace 过滤器重写 kramdown 生成的 <img src="/YYYY/..."> -->
{%- capture src_old -%}src="/2{%- endcapture -%}
{%- capture src_new -%}src="{{ img_prefix }}2{%- endcapture -%}
{{ content | replace: src_old, src_new }}
```

##### 2. `_layouts/home.html` — 首页 featured 轮播
```liquid
{%- assign img_prefix = site.image_prefixes.first.prefix -%}
{%- assign feat_path = post.image | remove_first: '/' -%}
{%- assign feat_url = img_prefix | append: feat_path -%}
<img src="https://images.weserv.nl/?url={{ feat_url | url_encode }}&w=900&h=500...">
```

##### 3. `_includes/post-card.html` — 文章列表卡片
```liquid
{%- assign img_prefix = site.image_prefixes.first.prefix -%}
{%- assign card_path = post.image | remove_first: '/' -%}
{%- assign card_url = img_prefix | append: card_path -%}
<img src="https://images.weserv.nl/?url={{ card_url | url_encode }}&w=400&h=260...">
```

##### 4. `_includes/head.html` — SEO og:image / twitter:image
```liquid
{% if page.image and page.image != '/' %}
{%- assign img_prefix = site.image_prefixes.first.prefix -%}
{%- assign og_img_path = page.image | remove_first: '/' -%}
{%- assign og_image_url = img_prefix | append: og_img_path -%}
<meta property="og:image" content="{{ og_image_url }}">
<meta name="twitter:image" content="{{ og_image_url }}">
{% endif %}
{% seo %}
```

注：jekyll-seo-tag 仍会输出自己的 og:image（用 `absolute_url`，缺 `/img/`），但我们的正确版本在 HTML 中先出现，社交平台取第一个。

#### 验证结果（全部通过）

| 检查项 | 结果 |
|--------|------|
| 文章内容图 `src` | `https://lishuhang.me/img/YYYY/...` ✅ |
| 文章封面图 weserv proxy | `lishuhang.me%2Fimg%2FYYYY%2F...` ✅ |
| 文章封面图 `data-original` | `https://lishuhang.me/img/YYYY/...` ✅ |
| 首页 featured 轮播 | `lishuhang.me%2Fimg%2FYYYY%2F...` ✅ |
| 首页 post-card 缩略图 | `lishuhang.me%2Fimg%2FYYYY%2F...` ✅ |
| og:image / twitter:image | `https://lishuhang.me/img/YYYY/...` ✅ |
| 图片 HTTP 加载 | 200 ✅ |
| 插件痕迹 | 0（完全移除）✅ |

#### 关键技术决策

**为什么用 `replace` 而非 regex？**
Liquid 的 `replace` 过滤器只支持字面字符串替换，不支持 regex。但所有图片路径都以 `/YYYY/` 开头（年份 2006-2026），所以用 `src="/2` 作为匹配前缀即可可靠匹配所有图片路径，不会误伤 `/assets/`、`/posts/` 等非图片路径。

**为什么用 `site.image_prefixes.first.prefix`？**
当前 `_config.yml` 中两个 date range 使用相同 prefix（`https://lishuhang.me/img/`），取 `.first.prefix` 即可。如果未来需要按日期区间使用不同 prefix（如迁移到新存储），需要更复杂的 Liquid 逻辑或重新引入插件。

**为什么 `remove_first: '/'`？**
`page.image` 存储为 `/2026/06/02/slug/01.jpg`（以 `/` 开头）。`site.image_prefixes.first.prefix` 是 `https://lishuhang.me/img/`（以 `/` 结尾）。直接拼接会产生双斜杠 `...img//2026/...`。用 `remove_first: '/'` 移除 `page.image` 的第一个 `/`，再拼接即得到正确 URL。

## 七、Agent 避坑指南（重要！）

### 1. 微信反爬"环境异常"

微信对服务器 IP 越来越严格，直接 `requests.get()` 返回验证页而非文章。z-ai `page_reader`（基于云端浏览器）也未能绕过本次反爬。

**规避方法**:
- 对于已发布文章，可从镜像站（36kr、新浪等）获取内容
- 对于新文章，需要用户手动保存 HTML 后用本地文件处理
- 不要相信"重试就能绕过"——微信的反爬是 IP 级别的，重试无效

### 2. Jekyll 插件 vs 皮肤级 Liquid

**教训**: Jekyll 4 的 `:post_render` hook 修改 `post.output` 在某些构建环境下不可靠。即使日志显示 rewrite 成功，实际部署的 HTML 可能未持久化。

**最佳实践**:
- 能用 Liquid 在皮肤里解决的，就不要写插件
- 插件的 `:pre_render` hook 在 gem 插件（如 jekyll-seo-tag）之后运行，无法抢先
- Generator 修改 `post.content` 会被渲染器重新读取，丢失修改
- **皮肤级 Liquid 在模板渲染时直接构造 URL，不依赖 hook，100% 可靠**

### 3. Ruby `next` 在 `gsub` block 中有问题

`next md[0] if condition` 语法在 `gsub` block 中会导致 rewrite 计数正确但实际 output 不变。

**解决**: 改用 regex negative lookahead `(?!img/)` 在 regex 层面跳过匹配，避免在 block 内使用 `next`。

### 4. 封面图与内容图路径不同

- **内容图**: markdown `![](...)` → kramdown → `<img src="/YYYY/...">` (相对路径)
- **封面图**: `page.image` (front matter) → layout `absolute_url` → `<img src="https://lishuhang.me/YYYY/...">` (绝对 URL)
- **weserv 代理**: layout 进一步包装为 `https://images.weserv.nl/?url=https%3A%2F%2Flishuhang.me%2F2026%2F...` (URL-encoded)

**三种格式都需要不同的处理方式**。在皮肤级 Liquid 中，用 `remove_first: '/'` + `append: prefix` 统一处理相对路径；用 weserv proxy 包装时直接传入完整 URL。

### 5. GitHub Pages CDN 缓存

构建成功后，CDN 可能需要 1-2 分钟才反映新内容。调试时需要用 `?cb=$(date +%s)` 或 `Cache-Control: no-cache` header 绕过缓存。

### 6. img repo Pages 构建失败 (errored)

上传图片后，img repo 的 GitHub Pages 构建一度显示 "errored"。原因是 compress-images workflow 并发运行，频繁 push 导致 Pages 构建被取消。

**解决**: 等待 compress workflow 完成后，Pages 自动重新构建成功。无需手动干预。

### 7. Google Free Translate 速率限制

Google 免费端点没有明确的速率限制文档，但连续快速请求可能被临时封禁。脚本中每条间隔 0.3s，实测 224 条无问题。

**如遇速率限制**: 增大 `time.sleep(0.3)` 到 `0.5` 或 `1.0`。

### 8. Python `json` 模块作用域

在 `translate_batch_google_free` 函数内使用 `json.loads()` 时，因函数内 `import json as _json` 而外部 `json` 未导入导致 `NameError`。

**解决**: 函数内显式 `import json as _json` 并使用 `_json.loads()`。
