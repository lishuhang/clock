## 二、项目全程概览

项目最初是一个单文件 Cloudflare Worker 图像生成站点。前端 HTML、CSS 和 JavaScript 都嵌在 Worker 文件中的模板字符串内，浏览器端以 localStorage 保存配置与任务状态，Worker 负责把请求代理至上游图像生成服务。项目在这一时段先后经历了三条上游路线：**马良/Keydraw 的历史多通道架构**、**Keydraw/97api 的 KD 单通道**、**Squido 的 SQ 单通道与会话保活设计**，最终在 07-28 进入 **Pixmind（PM）半自动账户导入 + 生图双 Worker** 的新阶段。

| 阶段 | 主版本/产物 | 实际状态 | 变更原因 |
|---|---|---|---|
| 历史基线 | `gpt2-worker-v27.2.js` | 仅作功能来源与回滚参考 | 原马良上游被 Cloudflare Challenge 阻断，不能稳定由 Worker 代理。 |
| KD 路线 | `gpt2-worker-kd-v2.0` 至 `kd-v2.3` | **已冻结** | Keydraw 公开 Gift Key 被上游吊销；自定义 97api 付费 Key 才能继续使用。 |
| SQ 路线 | `sq-v1.0.js` | 已做 Worker、代理和保活原型，但**未形成可稳定免费生图能力** | Squido 注册与会话受第三方验证、额度发放和短期会话约束，自动注册不可行。 |
| PM 路线 | `gpt2-mailtm-validator-v1.0.js`、`gpt2-worker-pm-v1.1.js` | **当前最新开发方向**；两份 Worker 已部署，端到端账户/签到/生成仍待真实测试 | 用户改为半自动注册和账户导入思路，规避此前登录 API 500 及 Squido 会话路线的不确定性。 |

## 2026-07-22：初始架构梳理、V2EX 站点探索与 Keydraw 可用性验证

早期版本 `v27.2` 的结构被梳理清楚：这是单文件 Cloudflare Worker，前端全部内嵌，后端主要转发 `/api/*` 至马良镜像上游 `grok.17nas.com/local-api/*`，并包含图片代理。该版本支持注册、登录、额度、邀请、图像任务和若干模型，同时保留加水印、去水印以及若干 base64 alpha map 资源。该结构成为后续重构时识别“哪些是历史遗留、哪些可复用 UI 功能”的参照。

同日开始调研无需注册或无需邮箱的 GPT-Image-2 中转选择。部分候选站虽然宣称免费，但实际要求邮箱注册、回帖或其他交互，不符合前端用户免注册的原目标。随后发现 `keydraw.97api.com` 提供了可公开获取 Gift Key 的接口，并识别出文生图、图生图、任务轮询以及 OpenAI 兼容端点等调用线索。早期实测曾成功取得公开 Key、提交任务并获取可访问图片，因此形成“以 Keydraw 为单一上游”的技术方向。

这一阶段的重要历史结论是：马良上游已出现 Cloudflare 防护，不能作为可靠的 server-side 通道；Keydraw 在当时看似可以成为免注册替代，但其免费资格必须持续实测，不能仅依赖网页宣传或旧帖子信息。

## 2026-07-23 16:42：KD-v2.5 交接、Keydraw 单通道重构完成但调度存在严重卡死风险

截至 07-23 下午，项目已从历史多通道架构收敛为 Keydraw 单通道。KD 的前端和 Worker 均围绕 `keydraw.97api.com` 组织，用户侧不需要自建后端数据库，状态保存于 localStorage。历史的马良通道、账号池、邀请体系和签到逻辑被移除；水印/去水印功能则从 `v27.2` 恢复到 `kd-v2.1` 之后的版本中。KD 版本序列中，`kd-v2.0` 是移除马良后的合并基础，`kd-v2.1` 增加 Gift Key 与多自定义 Key 轮换，`kd-v2.2` 调整界面，`kd-v2.3` 至 `kd-v2.5` 为后续直接改名迭代，未全部保留为独立历史文件。

已完成的关键能力包括：Gift Key 优先、多个用户自定义 97api Key 的轮换；按 Key 跟踪额度耗尽状态；按 GMT+8 跨日重置；上游错误在前端任务列表内透传；轮询把 `status: "error"` 视为终止失败状态，避免错误被错误显示为 300 秒超时；以及水印/去水印 UI 的恢复。界面上将标题统一为“AI生图”，将额度信息集中显示在右上角，并移除了重复的画质档位控件。

然而，KD-v2.5 的最严重问题是：当所有 Key 都被标记为耗尽时，任务可能无限停留在“排队中”。根因是并发槽数根据可用 Key 数量计算；可用 Key 为空时并发上限为零，任务调度循环持续等待可用槽位而无法退出。上游的实际错误文案从原先预期的“日限额已用完”变为“5小时限额已用完”，使得部分错误关键词匹配失效，进一步提高了未被正确标记为失败的概率。建议的修复方向是：在调度等待中增加超时失败；在取得有效 Key 失败时立即结束任务；在错误提取中把泛化的“限额”纳入识别，而不是只匹配“日限额”。

这一阶段还留下了若干必须长期遵守的实现坑：

1. `HTML_CONTENT` 是反引号模板字符串。需要在内嵌前端 JavaScript 中表达字面量换行时，不应直接写会被外层模板解释的 `\n` 形式；当时以 `String.fromCharCode(10)` 规避了 textarea 的 split/join 语法问题。
2. 清理“死代码”前必须全局检索调用点。曾误删设置相关函数，导致设置齿轮触发 `ReferenceError`；也曾删除 DOM 后仍在 `onModelChange()` 中直接访问，导致 null 的 `.style` 访问异常。
3. 重构中被删除或改名的渲染函数，仍可能有旧调用点，例如 `renderTopbar()` 与 `renderStorageInfo()`。应逐一替换或保留明确的空实现。
4. Workspace 重建后，未纳入仓库的部署目录与 Wrangler 配置可能丢失；部署前的环境配置也可能不存在。因此必须先检查本地部署环境，而不是假设其仍然可用。
5. Cloudflare CDN 缓存会使刚部署后的静态验证误读旧版本，应使用带时间戳的 cache-busting 查询参数。前端升级测试遇到异常时，还应先清理旧 localStorage，防止旧数据结构（特别是空 `apiKeys`）干扰新版本。

## 2026-07-24 23:53：确认 Keydraw Gift Key 已被上游吊销，KD 通道失去免费可用性

用户随后反馈 KD-v2.3 在轮询阶段出现 `Invalid API key`。实测表明，Keydraw 页面返回的 Gift Key 已发生轮换，但无论使用新旧 Gift Key，直接调用 97api OpenAI 兼容端点均返回 401 的无效 Key 错误。由此确认问题不是 Worker 将用户输入的新 Key 格式化错误，而是 V2EX 免费 Gift Key 在 97api 后端已被撤销；前端在 `starting_generation` 阶段看到的错误就是轮询路径对 401 的透传。

对当时已知 V2EX 同类站重新核查后，结果是：部分站点已经下线，部分受到区域或 Cloudflare 限制，绝大部分站点要求账户注册或订阅；没有找到同时满足“无需注册、真正免费、可由 server-side 稳定使用”的替代上游。能够稳定继续使用的只有用户自行配置 97api 付费 Key；其他选择仅能作为注册后免费额度或人工操作的候选。

这一结论直接导致 KD 线路不再应继续追加版本。KD-v2.3 被作为冻结版本保留在仓库，线上同名 Worker 即使仍可打开，也不能再承诺免费生成可用。若未来用户提供合法付费 97api Key，KD 的多 Key 配置能力仍可作为付费路线参考，但不应再把失效 Gift Key 当作恢复对象。

## 2026-07-25 上午：冻结 KD 路线，调研 Squido 作为 SQ-v1.0 的候选上游

用户决定雪藏 KD，要求评估 Squido 免费档是否能够在**最终用户无需自行注册**的前提下重构为 `sq-v1.0`。本轮明确了核心约束：新版本必须去除 Keydraw 和马良的历史代码；若上游必须注册，则需要先确认是否存在合规、稳定的账户获取和维护方式；否则不应直接开始重构。

Squido 调研确认其免费档并非“6 张 GPT-Image-2/日”：它是每天 6 credits，而 GPT-Image-2 单张消耗 3 credits，因此实际为**每账户约 2 张/日**。其认证流程涉及邮箱一次性验证码和 Cloudflare Turnstile；前端虽然出现某些认证 SDK 痕迹，但实际会话 Cookie 后续被证实使用 BetterAuth 体系。直接请求发验证码接口会被要求提供 Turnstile 验证结果。临时邮箱部分域名能够通过邮箱格式校验，但这不代表可以自动完成 Squido 注册或稳定长期使用。

此时同时完成了更广泛的中转站与邮箱服务调研。公开临时邮箱 API 中，多个服务能够创建邮箱和读取邮件，且部分域名通过 Squido 的格式校验；但真正阻塞点不在收邮件，而在 Squido 的 Turnstile 与浏览器侧认证状态。横向比较后，Squido 是当时最接近“邮箱可注册 + 周期性免费额度 + GPT-Image-2”的候选，但也是唯一的严格候选，缺少同等可用的后备站。Playground 的 GPT-Image-2 免费额度极低，若干站点只有一次性赠额、必须手机或第三方登录、没有免费档，或受到更强的反自动化保护。

因此，本阶段形成的正确决策不是立即承诺自动账号池，而是先做有限的可行性验证：若用户能合法提供其自行注册的会话，Worker 可以做代理、轮换与会话健康检查；若无法稳定取得会话，则应考虑用户自有付费 Key 或重新选型。任何试图规避第三方验证、批量自动注册或滥用免费额度的实现均不应继续推进。

## 2026-07-25 21:30 至 22:38：Squido 浏览器可行性验证失败；SQ-v1.0 Worker 完成但无有效会话无法出图

07-25 晚间，对 Squido 的浏览器注册路径进行了可行性验证。结论是，容器化无头环境中无法稳定通过或加载其第三方验证组件；更换浏览器内核、常见无头参数和不同运行方式都未能得到可用于注册的验证结果。该结果说明：在现有环境中自动注册不是可靠功能，不能以“无人值守自动号池”作为交付承诺。后续不应重复投入时间尝试绕过第三方安全验证。

尽管无法自动取得会话，`sq-v1.0.js` 仍按“用户手工合法配置会话信息”的模式完成。它是一个去除 KD/马良历史元素的单通道 Worker，包含提示词、模型/比例/清晰度选择、任务列表和设置面板；可以保存多个会话条目并以使用时间轮换。Worker 路由覆盖生成提交、任务轮询、参考图上传和会话健康检查。根据前端资源分析，提交路径需经 Squido 网站的应用层接口，任务状态需经其图像 API 查询，参数使用 `resolution` 与 `ratio`，不是 OpenAI 风格单一 `size` 字段。

SQ-v1.0 已部署到原 `ai-image` Worker 名称，因此覆盖了当时的 KD 线上内容；但 `gpt2-worker-kd-v2.3.js` 源文件仍在仓库中，可用于必要时回滚。由于没有有效 Squido 会话，本轮未能完成用户指定的“生成一个 YouTube 首页，其中播放一些中文热门内容”的 16:9、1K 测试图，也没有产生应提交的 sample 图片。应明确记录为：**界面与代理框架已完成；真实可生成性未完成验证。**

## 2026-07-26 09:13：修正 Squido 认证与 API 路径认知，代理验证通过但账户额度为零

用户随后提供了浏览器导出的 Cookie 文件，并报告页面报错。此次修复和验证得出几个关键事实：

1. Squido 的实际会话 Cookie 是 `__Secure-better-auth.session_token`，而不是此前推断的 `__session`。以 `eyJ...` 开头的 session data 不是应单独填入的主会话值。
2. 设置页面改为支持粘贴整段 Netscape 格式 Cookie 文件、标准 `name=value` 形式或仅 Cookie 值；前端会提取主 session token。多个账户使用空行区隔。
3. `SESSION_HEADER is not defined` 的根因是浏览器内嵌脚本错误引用了 Worker 顶层常量。修复为前端自行定义请求头名，不再跨运行环境引用未定义变量。
4. 提交路径大小写被修正为 `/api/generate/image`；此前使用大写 `Image` 会导致 404。
5. Worker 访问上游时需要显式设置 Cookie 并使用合理的浏览器请求头；否则上游防护可能按 Worker 默认标识拒绝请求。

修复后的 Worker 对会话检查和签到/额度查询代理能够返回正常响应，说明 Cookie 传递和 API 路径基本正确。用户提供的会话可被上游识别，但账户信用额度为零；实际提交生成返回“额度不足”。因此，阻塞测试图生成的因素是上游账户未获可用 credits，而不是本次 Worker 路径或 Cookie 格式。推测可能涉及新账户到账延迟、上游风控或其自身业务规则，但在未获得上游确认前不能将任一推测作为事实。

此阶段还确认 BetterAuth 会话具有有限期限，且可能在接近到期时通过 `Set-Cookie` 进行滑动续期。Worker 已将上游的 Set-Cookie 转为浏览器可读的自定义响应头，为后续前端自动更新本地会话提供基础；但当时前端尚未完成实际更新逻辑。

## 2026-07-26 10:26：评估“号池管理器”需求，结论是优先做会话续期而不是复杂账户自动化

用户担心临时邮箱账户保活、Squido 会话过期后无法重新收验证码，以及管理多个邮箱密码的成本。对这个问题重新拆解后，真正需优先解决的是会话能否在正常使用中持续续期，而不是先开发一个复杂的邮箱号池管理器。

调研显示，临时邮箱账户自身可以在一定活跃周期内保持；但 Squido 的重新登录仍依赖浏览器侧交互和第三方验证。即使系统能够读取邮箱内的验证码，也不能可靠替代浏览器认证流程中的内部状态。因此，“由 Worker 完全自动重新登录并维护号池”的方案不可作为当前可行承诺。相对而言，若 BetterAuth 在会话接近过期时返回新 Cookie，前端捕获后更新 localStorage，用户定期使用或主动健康检查即可显著降低重新登录需求。

由此形成了优先级：第一阶段应实现 Set-Cookie 自动捕获、会话剩余时间展示和一键健康检查；只有在用户明确需要、且第一阶段不足时，才评估人工辅助的邮箱验证码查看流程。完全自动化的账户重建不在后续范围内。需要注意，混合认证实现的蛛丝马迹较多，不能简单假设 Squido 是纯 Clerk 或纯 BetterAuth；实际需要以浏览器导出的 Cookie 和已验证接口为准。

## 2026-07-26 10:46：SQ-v1.0 增加 KV、定时触发与会话保活原型，长期续期尚待到期窗口验证

用户提出了更直接的想法：在会话到期前（例如 6.5 天阈值）由 Worker 自行调用低风险查询接口，以触发滑动续期。该想法被实现为 SQ-v1.0 的会话保活原型。

实现包括：前端解析已知会话信息并在请求响应中检查自定义的会话更新头；会话保存后同步到 Cloudflare KV；Worker 提供保存、加载和人工触发保活检查的端点；定时任务每日运行，遍历 KV 中已保存的条目，对接近过期者调用上游用户信息接口，若上游返回新的 Cookie 则更新 KV。前端本地存储仍被视为用户设备上的即时来源，KV 是供定时保活和跨会话恢复使用的备份。

已验证的范围是：KV 可写入和读取；人工触发可遍历已保存条目；Worker 能使用真实会话调用上游信息接口并记录本次检查时间。由于当时会话距离过期还较远，上游没有返回新的 Set-Cookie，这是滑动续期机制的预期表现，而不是失败。真正的“自动续期永久可用”仍需在会话接近到期窗口时验证是否确实返回新 Cookie，不能提前宣称已稳定实现。

这一原型还存在明确风险：KV 写入可能有短暂最终一致性延迟；定时频率有限；如果用户清理本地状态，KV 中旧会话可能继续被尝试保活；不同设备因本地随机标识不同可能出现同一会话重复存储；手动保活入口如果没有访问控制可能被滥用。更重要的是，保活只能处理仍有效且可续期的会话，不能解决账户额度为零，也不能替代过期后的重新认证。

截至该时点，SQ 路线的实际状态仍是：会话代理和保活技术原型存在，但免费账户额度问题未解决，真实测试图未生成，不具备可承诺的免费生产能力。

## 2026-07-28 12:25：转向 Pixmind（PM）半自动注册与账户导入方案，明确双 Worker 架构

在 Squido 路线无法可靠解决注册、额度和会话维护问题后，工作转向 Pixmind.io 的 PM 通道。用户提出半自动模式：不再追求无人工参与的注册；先做一个邮件管理 Worker 协助用户创建并管理用于注册的邮箱、查看验证码和导出账户信息；再让图像 Worker 导入用户已合法注册的账户，使用 token 进行账户轮换、余额查询、签到与图像生成。

该方案将系统拆为两个 Worker：

| 组件 | 规划文件 | 职责 | 状态（07-28 12:25 规划时） |
|---|---|---|---|
| 邮箱管理端 | `gpt2-mailtm-validator-v1.0.js` | 创建/管理邮箱、读取收件箱、辅助用户查看注册验证码、调用 Pixmind 登录以获取账户标识与 token、导出账户 JSON。 | 规划完成，优先实现。 |
| PM 图像端 | `gpt2-worker-pm-v1.1.js` | 导入账户 JSON、轮换可用账户、查询余额/签到、代理文本生图、轮询任务、代理图片。 | 规划为基于 SQ 前端框架改造。 |

账户数据的逻辑结构被定义为邮箱、密码、用户标识、访问 token、额度、最近签到日、最近使用时间和禁用状态等字段。前端 localStorage 保存账户列表。对于可用账户选择，计划使用最久未用优先的轮换方式，跳过禁用或余额为零的账户；每日刷新则由前端定时检查并对用户已授权账户发起签到/额度刷新。该设计只应服务于用户本人合法提供和控制的账户，不能扩展为批量自动注册或规避第三方限制。

原规划同时注明了一个已知阻塞：Pixmind 的 `emailPassword` 登录路径曾返回 500。邮箱管理 Worker 可以把该失败明确呈现给用户，但不能承诺通过后端模拟登录修复第三方服务异常；如该问题持续，备用方案是用户在 Pixmind 浏览器内完成合法登录后自行导出其访问 token，并在导入 JSON 中配置，而不是反复试图自动化绕过登录流程。
