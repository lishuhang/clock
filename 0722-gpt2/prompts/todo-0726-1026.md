### 1.1 用户描述的痛点 vs 实际问题

| 用户描述 | 实际问题 |

### 1.2 真正需要解决的核心问题

**只要让 squido session 永不过期, 用户就不需要重新走 OTP 流程, 也就不需要管 mail.tm 凭据**。

squido session 过期的两个时间点:
- `__Secure-better-auth.session_data` cookie: 2 天 (但 BetterAuth 会自动续期)
- `__Secure-better-auth.session_token` cookie: 9 天 (BetterAuth 也会续期)
- BetterAuth session 本身: 7 天 (可通过 API 调用触发续期)

**关键发现**: BetterAuth 在每次 API 调用时, 如果 session 快过期, 会通过 `Set-Cookie` 返回新的 session_data 和 session_token, 实现"滑动续期" (sliding session)。

只要 worker 在 session 过期前调用过任何 squido API (比如生成图片、查 credits), BetterAuth 就会续期, worker 捕获 Set-Cookie 就能更新 stored cookie, 实现"永久保活"。

### 2.2 squido `signIn.emailOtp` 实现

**发现位置**: 6450-ebb7d89101b70834.js chunk

**代码**:
```js
F = async e => {
  e.preventDefault();
  g(!0);
  w("");
  try {
    let {data: e, error: t} = await c.U.signIn.emailOtp({email: m, otp: C});
    if (t) throw Error(t.message || s("errors.invalidCode"));
    if (e.user) h(), L();

  } catch (e) {
    w(e.message || s("errors.invalidCode"));
  } finally {
    g(!1);
  }

```

**分析**:
- `c.U` 是 Clerk SDK 实例 (从其他地方看到 `c.U.useSession()` 等 Clerk hooks)
- `signIn.emailOtp({email, otp})` 是 Clerk SDK 调用
- **不需要 Turnstile token** (Turnstile 只在 `send-email-otp` 阶段需要)

**关键推断**: squido 同时使用 Clerk SDK (前端 UI + email OTP) 和 BetterAuth (后端 session 管理)。session cookie 是 BetterAuth 的 (`__Secure-better-auth.session_token`), 但 email OTP 流程走 Clerk API。

### 2.3 关键问题: 能否自动重新登录 squido?

**完整 email OTP 流程**:
1. 浏览器加载 `/ai-image-generator`, 用户输入 email
2. squido 前端渲染 Turnstile widget, 用户通过 (headless 不行)
3. 前端 POST `/api/auth/send-email-otp` body `{email, turnstile_token}` → squido 后端发 OTP 邮件
4. Clerk 后端创建 `sign_in_id` (内部 ID, 前端通过 Clerk SDK 状态管理)
5. 用户从邮箱读取 6 位 OTP
6. 前端调 `signIn.emailOtp({email, otp})` → Clerk 验证 OTP
7. 验证通过 → squido 后端创建 BetterAuth session, 返回 `__Secure-better-auth.session_token` cookie

**自动化阻塞点**:
- ❌ Step 2 (Turnstile): headless 不可绕过, 需要用户在浏览器手动操作
- ❌ Step 4 (sign_in_id): Clerk 内部状态, worker 拿不到 (Clerk SDK 在浏览器中管理)
- ✅ Step 5 (收 OTP): worker 可以用 mail.tm API 自动收
- ❌ Step 6 (verify OTP): 需要 sign_in_id, 这个 ID 在浏览器 Clerk SDK 状态中

**结论**: 即使 worker 拿到 OTP, 也无法直接调 `signIn.emailOtp` (因为 sign_in_id 在浏览器中, 不在 worker)。必须由浏览器中的 Clerk SDK 完成验证。

**所以**:
- 完全自动化的"号池管理器"在当前架构下**不可行**
- 半自动化 (用户在浏览器操作, worker 辅助收 OTP) 可行, 但用户体验没比手工好多少

### 2.4 BetterAuth Set-Cookie 续期机制验证

**已实现**: sq-v1.0 worker 在 `handleProxy` 中捕获 `Set-Cookie`, 通过 `X-Squido-Set-Cookie` response header 返回给前端 (todo-0726-0913 §2.6)。

**未实现**: 前端没有读取这个 header 并更新 localStorage 中的 token。需要补充前端逻辑。

**预期效果**: BetterAuth 在 session 接近过期时会自动续期。worker 每次 API 调用都会触发 BetterAuth 检查, 如果需要续期就发 Set-Cookie。前端读 `X-Squido-Set-Cookie` 更新 stored token, 实现"滑动续期"。

## 3. 解决方案对比

### 方案 A: Set-Cookie 自动续期 (推荐 ⭐⭐⭐⭐⭐)

**思路**: 让 squido session 永远不过期, 用户配置一次后永远不用动。

**实现**:
1. 前端在每次 apiFetch 后检查 `X-Squido-Set-Cookie` header
2. 如果有, 解析出新的 `__Secure-better-auth.session_token=...`, 更新 localStorage
3. 用户每周用一次 worker (生成图片或查询 credits), 触发 BetterAuth 续期
4. session 永不过期 (只要用户不连续 7 天不使用)

**工作量**: 30 分钟前端编码

**用户体验**:
- ✅ 配置一次后永远不用动 (只要每周用一次)
- ✅ 不需要管理 mail.tm 账号
- ✅ 不需要重新登录 squido
- ⚠️ 如果用户连续 7 天不用, session 过期, 需要重新登录

**适用场景**: 个人用户, 每周至少用一次

### 方案 B: 半自动号池管理器 (推荐 ⭐⭐⭐)

**思路**: 多账号轮换, 每个账号 7-9 天过期, 但只要不同时过期总有可用账号。

**实现**:
1. 前端 localStorage 存多个 squido session_token + 对应 mail.tm 凭据 (email + password)
2. Worker 新增 `/api/mailtm-login` (登录 mail.tm 拿 JWT) 和 `/api/mailtm-get-otp` (轮询 mail.tm 收件箱找 OTP)
3. Worker 新增 `/api/squido-verify-otp` (调 Clerk signIn.emailOtp — 但这个**实际上不可行**, 因为 sign_in_id 在浏览器)
4. 替代方案: worker 只负责收 OTP, 用户在浏览器手工完成 verify

**工作量**: 1-2 小时编码

**用户体验**:
- 用户每周需要: ① 在浏览器中输入 email + 通过 Turnstile + 点 Continue, ② worker 自动从 mail.tm 拿 OTP 显示给用户, ③ 用户手工填 OTP 到浏览器, ④ 复制新 cookie 到 worker
- 比纯手工稍快但复杂度大增

**适用场景**: 多账号重度用户, 愿意接受半自动流程

### 方案 C: 完全自动号池管理器 (不推荐 ⭐)

**思路**: 接 2Captcha 等第三方 CAPTCHA 服务自动绕 Turnstile。

**问题**:
- 持续成本 ¥0.05/次
- 1-2 天工作量
- squido 改反爬策略就崩
- 法律灰色 (违反 ToS)

**适用场景**: 不推荐, 除非方案 A 和 B 都无法满足

### 方案 D: 用户手工重新登录 (最简单 ⭐⭐⭐⭐)

**思路**: 不做任何自动化, 用户在 session 过期时手工重新登录。

**实现**: 无需编码, worker 前端显示 session 剩余天数提醒。

**用户体验**:
- 每 7-9 天用户需要: ① 在浏览器手工登录 squido (5 分钟), ② 复制 cookie 到 worker
- 总维护成本: 每周 5 分钟

**适用场景**: 单账号轻度用户

### Phase 1 (立刻可做, 30 分钟): 方案 A

**实现步骤**:

1. **前端添加 Set-Cookie 自动捕获逻辑**:
```js
// 在 apiFetch 函数中, 收到响应后检查 X-Squido-Set-Cookie
async function apiFetch(path, options) {
  const opts = options || {};
  const headers = opts.headers || {};
  if (opts._sessionToken) {
    headers[SQ_COOKIE_HEADER] = opts._sessionToken;
  }
  if (opts.body) headers['Content-Type'] = 'application/json';
  const r = await fetch(path, {
    method: opts.method || 'GET',
    headers,
    body: opts.body,
  });
  // 检查 Set-Cookie 续期
  const setCookie = r.headers.get('X-Squido-Set-Cookie');
  if (setCookie) {
    // 解析出 __Secure-better-auth.session_token=NEW_VALUE
    const match = setCookie.match(/__Secure-better-auth\.session_token=([^;]+)/);
    if (match) {
      const newTokenValue = match[1];
      const newCookieStr = '__Secure-better-auth.session_token=' + newTokenValue;
      // 更新 state 中的 token
      const tokenEntry = state.tokens.find(t => t.token === opts._sessionToken);
      if (tokenEntry) {
        tokenEntry.token = newCookieStr;
        tokenEntry.lastRefreshed = Date.now();
        saveState();
        renderQuotaBadge();
        console.log('Token auto-refreshed for', tokenEntry.label);
      }
    }
  }
  // 检查 token 是否失效
  const tokenValid = r.headers.get('X-Squido-Token-Valid');
  if (tokenValid === 'false') {
    const tokenEntry = state.tokens.find(t => t.token === opts._sessionToken);
    if (tokenEntry) {
      tokenEntry.expired = true;
      saveState();
      renderQuotaBadge();
    }
  }
  return r;
}
```

## 7. 突出问题与避坑 (给下个 agent)

### 7.1 ⚠️ squido 同时用 Clerk SDK + BetterAuth (混合架构)

**发现**: JS chunks 中既有 Clerk SDK 调用 (`signIn.emailOtp`, `useSession`), 又有 BetterAuth cookie (`__Secure-better-auth.session_token`)。

**推断**: squido 可能:
- 用 Clerk SDK 处理前端 auth UI 流程
- 用 BetterAuth 做后端 session 管理 (cookie 颁发)
- 两者通过某个 adapter 集成

**避免**: 后续 agent 不要假设 squido 是纯 Clerk 或纯 BetterAuth, 两者都可能涉及。

### 7.2 ⚠️ Clerk signIn.emailOtp 需要 sign_in_id (在浏览器中)

**问题**: 即使 worker 拿到 OTP, 也无法直接调 Clerk signIn.emailOtp, 因为 sign_in_id 是 Clerk SDK 在浏览器中维护的内部状态。

**避免**: 不要试图完全自动化 squido 登录流程。要么用户在浏览器手工完成 verify, 要么用 Playwright 之类控制浏览器 (但 Turnstile 阻塞)。

### 7.3 ⚠️ mail.tm JWT 无 exp 但账号 7 天不登录会被清理

**问题**: 解码 mail.tm JWT 发现没有 exp 字段, 但服务端有"7 天不活跃清理账号"的策略。

**避免**: 如果做 Phase 2 号池, 必须每周自动登录所有 mail.tm 账号一次 (Cron Trigger)。

### 7.4 ⚠️ BetterAuth Set-Cookie 续期不一定每次都发

**问题**: BetterAuth 通常在 session 接近过期时才发 Set-Cookie 续期, 不是每次 API 调用都发。worker 的 X-Squido-Set-Cookie header 大多数时候为空。

**避免**: 前端逻辑要兼容"Set-Cookie 为空"的正常情况, 不要每次都期望有续期。

### 7.5 ⚠️ Worker 前端不能直接读 Set-Cookie (CORS 限制)

**问题**: 浏览器 fetch 默认不能直接读 `Set-Cookie` response header (被 CORS 禁止)。所以 worker 把上游的 Set-Cookie 复制到自定义 header `X-Squido-Set-Cookie` 暴露给前端。

**已实现**: worker 的 `corsHeaders()` 中已经把 `X-Squido-Set-Cookie` 加到 `Access-Control-Expose-Headers`。

**避免**: 前端读 `r.headers.get('X-Squido-Set-Cookie')`, 不要直接读 `Set-Cookie`。
